# 业务逻辑

## 发送平台分流

### 业务规则

短信发送采用“平台 Hook + 模板存在性 + 权重”三层选择，而不是把供应商写死在业务调用方中。这样可以在不改变调用方 `send()` 参数的情况下切换供应商或按比例分担成本/容量。

- 内置发送平台由 `poppy.sms.send_type` 注册：`local`（本地）、`aliyun`（阿里云）、`chuanglan`（创蓝）、`lianlu`（联麓）、`volc`（火山云）。每个平台 Hook 同时声明展示名称、Provider 类和（除本地外）设置页。
- `Sms::rateSmsDriverByType($type)` 只把“存在该短信类型模板”的平台放入候选集合，然后读取 `py-sms::sms.send_rate_{scope}` 的整数权重。
- 权重只接受 `0` 到 `100`。大于零的平台参与随机选择；多个平台按权重随机，一个平台时直接使用该平台。
- 没有任何有效权重时，选择 `local`。如果请求类型没有候选模板，也会回退到 `local`，最终由本地驱动返回“请设置短信模板”。
- `Factory::instance()` 的无类型入口使用所有已配置的有效平台权重；容器中的 `SmsProvider::send()` 则按具体短信类型重新筛选模板候选。

### 路由/分发规则

| 条件 | 处理路径 |
|---|---|
| 只有一个平台具有该类型模板且权重为正 | 直接实例化该平台 Provider |
| 多个平台具有模板且权重为正 | 按 `send_rate_{scope}` 做随机权重选择 |
| 没有有效权重 | 选择 `LocalSmsProvider` |
| 选中的平台没有该类型模板 | 发送前校验失败，不向供应商发请求 |
| 供应商返回失败 | 保存 Provider 错误并返回 `false`，不会自动尝试下一个平台 |

### 状态机

```text
调用请求
  ├─ 手机号/类型/模板/签名缺失 → FAILED（本地错误，不发供应商请求）
  └─ 候选平台过滤 → 权重选择 → Provider 请求
                         ├─ 成功 → SUCCESS
                         └─ 供应商失败/SDK 异常 → FAILED（setError，当前调用结束）
```

状态说明：

- `FAILED` 不会进入模块内 `RETRY` 状态；本模块没有 Job、退避时间或统一重试次数。
- 发送失败也不会触发第二个供应商。所谓“回退”只发生在发送前没有有效权重时回到本地平台，不是故障转移。

## 模板类型与模板代码映射

### 业务规则

模板类型是稳定的业务语义，供应商模板代码是平台实现细节。当前基础配置只声明 `captcha`（验证码）类型，并允许继续扩展类型；调用方只需传入类型名和参数，不应依赖供应商 SDK 的请求结构。

- `Sms::establish($id, $code)` 使用 `{scope}:{type}` 作为设置键，例如 `aliyun:captcha`，并保存 `scope`、`type`、`code` 三个字段。
- 阿里云的 `code` 作为 `SendSmsRequest::templateCode`，`params` JSON 编码后作为 `templateParam`。
- 联麓的 `code` 作为模板 ID，参数使用 `array_values($params)` 传入模板参数集合。
- 创蓝通过 `sys_trans($code, $params)` 生成短信内容，再根据国内/国际手机号调用不同 API；火山云把 `code` 作为 `TemplateID`，参数编码为 `TemplateParam`。
- 本地驱动把 `code` 当作 Laravel 翻译写法交给 `sys_trans()`；`resources/config/sms.php` 明确说明本地模板可使用如 `code` 的变量。
- 仅验证 `type` 在已注册类型中、`scope` 存在、`code` 非空；没有对不同供应商的模板 ID 格式或参数名称做统一校验。这样保留了供应商模板的自由度，但配置错误会延迟到发送时暴露。

### 关键算法/计算

- 模板键：`$scope . ':' . $type`。
- 权重键：`py-sms::sms.send_rate_{$scope}`。
- 阿里云手机号：`PySmsHelper::transToAliyunMobile()` 去除 `-` 并用逗号连接多个号码。
- 火山云手机号采用同样的去 `-`、逗号连接规则。

## 签名处理

### 业务规则

签名是所有实际发送平台的共同前置条件。默认签名来自系统设置 `py-sms::sms.sign`，调用 `send()` 时传入的非空 `$sign` 优先级更高；没有任何签名时，`BaseSms::checkSms()` 直接拒绝发送。

不同供应商按自身协议包装签名：

| 平台 | 发送时的签名处理 |
|---|---|
| 本地 | 日志内容前加 `[签名]` |
| 阿里云 | 原样写入 `signName` |
| 创蓝 | 移除已有中英文括号后统一包装为 `【签名】`，并拼到短信正文前 |
| 联麓 | `LianLu\SmsApi` 构造时把签名包装为 `【签名】`；当前模板短信调用 `sendTemplateSMS()`，该路径不会把 `signName` 拼到短信正文 |
| 火山云 | 原样写入请求体 `Sign` |

签名存储是全局系统设置，不按模板记录独立签名；供应商设置页只维护凭据/账号，不维护签名。

## 限流、频率上限与幂等

### 业务规则

分流比例不是频率上限：`send_rate_*` 的 0–100 数值只决定平台被选中的相对概率，不代表每个手机号、IP 或时间窗口的可发送条数。

- SMS 模块没有手机号级、IP 级、模板级频率计数器，也没有重复请求幂等键。
- 系统验证码入口在生成验证码前负责请求节流和验证码发送节流；后台入口还会检查账号存在性。这些是上游业务规则，短信模块只接收最终的发送参数，相关跨模块事件契约见 `contracts.md`。
- 直接调用 `SmsContract::send()` 的业务方不会自动获得上述验证码限流保护；如果该调用属于验证码场景，限流必须由调用方先完成。

## 失败与重试策略

### 业务规则

发送是同步操作，错误需要由调用方决定是向用户返回失败、记录告警还是自行重试。

- `BaseSms::checkSms()` 处理手机号、类型、模板和签名缺失，避免无效请求触达供应商。
- 阿里云和火山云在供应商业务响应失败时调用 `setError()`；缺少对应 SDK 时抛出 `SmsException`，这两类 Provider 会捕获该异常并返回 `false`。其他未被捕获的 SDK、网络或 JSON 异常仍可能向调用方抛出。
- 创蓝和联麓的 cURL/API 返回值由各自 Provider 解码；非成功状态会写入 Provider 错误。
- `SmsProvider::send()` 只把被选中驱动的错误向上返回，不捕获后切换其他驱动。
- 没有队列 Job、指数退避、死信或发送状态持久化。外部调用方若要重试，必须自行控制次数，并避免重复验证码或突破上游限流。

## 发送日志

### 业务规则

日志是按 Provider 实现分散记录的调试/运行信息，不是完整的发送审计能力：

- `LocalSmsProvider` 使用 `sys_info()` 记录带签名的翻译后短信内容，用于未选择真实平台时查看验证码内容。
- `VolcSmsProvider` 使用 `Logging::logger('Sms')` 记录 `volc.request` 和 `volc.response`，包括请求体和供应商响应。
- 阿里云、创蓝、联麓没有在模块内写入统一成功日志；失败信息保存在 Provider 的错误状态中，由上层处理。
- 日志可能包含手机号、模板参数或验证码，生产环境应按宿主日志脱敏策略处理；模块未提供独立脱敏或审计表。

## 管理配置规则

| 配置项 | 规则 | 原因 |
|---|---|---|
| 模板 `scope` | 建立时必须选择平台；编辑既有模板时平台不可修改 | 模板键由平台和类型组成，修改平台会改变标识 |
| 模板 `type` | 必填，且必须属于 `config('poppy.sms.types')` | 防止调用不存在的业务短信类型 |
| 模板 `code` | 必填，内容由平台解释 | 本地需要翻译写法，远端平台需要模板 ID/模板内容 |
| 签名 | 可为空保存，但实际发送前必须存在 | 允许先保存后台表单，发送时再明确报错 |
| 分流比例 | 每个平台为整数 `0..100` | 防止随机选择器收到负数或异常比例 |
| 供应商凭据 | 表单均为可空 | 配置页不验证远端凭据，连接性在实际发送时验证 |

## 定时任务 / Artisan 命令

本模块没有 `Commands`、`Jobs` 或调度注册。短信发送、模板保存和平台设置均由 HTTP 表单或外部业务调用直接触发。

## 中间件规则

| 中间件/权限 | 应用范围 | 规则 |
|---|---|---|
| `backend-auth` | 全部短信后台路由 | 必须通过管理后台认证 |
| `backend:py-sms.global.manage` | `SmsController`、`StoreController` | 控制模板 CRUD、总设置和供应商凭据设置 |

## 待确认

- “发送失败后自动切换供应商”是否是产品要求：当前代码只实现发送前的权重选择和无权重时的本地回退，没有失败重试或故障转移。
- 发送比例是否确实只表示流量权重，还是还应承担手机号/时间窗口频率限制；当前未发现 SMS 模块的频率计数实现。
- 统一发送日志、供应商回执和验证码脱敏是否由宿主模块负责；当前 Provider 实现没有共同审计接口。
- `scope` 只做必填校验，没有调用 `Sms::kvPlatform()` 做合法值校验；是否需要限制为当前 Hook 注册的平台需确认。

> 具体事件、监听方和跨模块发送入口见 [contracts.md](contracts.md)；完整调用链见 [flows.md](flows.md)。
