# 业务逻辑

## 词库维护策略

### 业务规则

- **单条与批量新增共用一个入口**：后台只提供一个多行文本框；一行可表示一个词，因此单条新增是批量新增的特例。这样可以让运营人员一次粘贴一组词，同时避免为单条和批量维护两套校验与缓存逻辑。
- **允许“部分新增”**：提交内容会先整体 `trim`，再按当前系统的 `PHP_EOL` 分行并过滤空行。数据库已存在的词会被忽略，只插入差集；只要存在至少一个新词，整个操作即成功。该策略适合重复粘贴运营词表，不要求调用方预先去重。
- **全量重复视为业务错误**：若提交的所有词都已存在，则返回“没有需要添加的敏感词, 输入内容存在重复数据”，避免给操作人员造成“已新增”但数据库未变化的错觉。
- **删除为物理删除**：支持单个 ID 和 ID 数组，不设置软删除或启停状态。词库的语义是“当前生效集合”，删除后该词不再属于下一次构建的字典。
- **写后失效、读时重建**：后台新增或删除成功后只删除 `dict` 缓存，不在写请求中同步重建 Trie。下一次检测发生时再从数据库加载并建树，以缩短管理写请求耗时并把构建成本推迟到真实需要检测时。
- **没有编辑语义**：`Action\Word` 只提供 `establish()`（新增）和 `delete()`；没有按 ID 更新词文本的方法。词条变更实际应通过“删除旧词 + 新增新词”表达。

完整管理链路见 [flows.md](flows.md) 的“敏感词管理 CRUD 流程”。

### 数据约束

| 约束 | 当前规则 | 业务含义 |
|---|---|---|
| 提交字段 | `word` 必填且必须为字符串 | 只接受文本词表，不接受结构化数组导入 |
| 分隔方式 | 按 `PHP_EOL` 分行 | 后台文本框以“一行一个”为约定 |
| 空行 | `array_filter()` 后忽略 | 粘贴词表可包含空白行 |
| 已存在词 | 查询后从待插入集合排除 | 重复提交时保留新词、跳过旧词 |
| 数据库存储 | `word` 为 `varchar(50)` | 单个词的持久化上限由数据库列决定 |
| 状态 | 无启用、停用、审核字段 | 表内存在即参与下一次词典构建 |

## 检测结果模式

模块将“如何检测”和“业务如何处置”分开：`sensitive_words()` 只返回检测结果，调用业务自行决定拦截、展示提示、保存替换文本或提交人工复核。常量及返回契约见 [contracts.md](contracts.md)。

| 模式 | 结果策略 | 为什么这样处理 |
|---|---|---|
| `check`（拦截判断） | 首次确认命中即可停止；合法返回 `true`，非法返回 `false` | 适合提交前门禁，只需要知道“能否通过”，短路可减少无意义扫描 |
| `words`（复核素材） | 扫描文本并返回命中词数组 | 为日志、提示或调用方人工复核提供命中依据；本模块本身不创建审核单 |
| `replace`（展示替换） | 每个命中词按 Unicode 字符数替换为等长 `*` | 隐藏敏感内容的同时大致保持原文本长度和排版；替换只作用于返回值，不回写业务数据 |

`words` 与 `replace` 都会开启“查找全部”模式，因而通常比只求布尔结果的 `check` 成本更高。模块没有独立的“review 状态”；所谓复核模式是调用方消费 `words` 返回值后自行实现审核流程。

## Trie 算法选择与匹配规则

### 选择依据

- **共享前缀以降低词库存储重复**：多个词具有共同前缀时，Trie 复用字符节点，比为每个词反复执行全字符串比较更适合固定词库、多次检测的场景。
- **按 Unicode 字符建树**：使用 `mb_strlen()` / `mb_substr(..., 'utf-8')`，使中文敏感词按字符而非字节匹配，替换星号数也与字符数一致。
- **词库读多写少**：Trie 构建完成后进入标签缓存，并由进程内静态变量复用；管理写操作只负责让共享缓存失效。这一取舍优先优化重复检测，而非高频词库写入。
- **实现保持轻量**：节点只依赖自定义 `HashMap` 和 `ending` 标记，不引入外部算法包。当前没有 AC 自动机的 failure link，因此实现复杂度较低，但最坏扫描复杂度高于 AC。

代码仓库没有算法选型 ADR；以上是从现有结构可验证出的工程取舍，历史选型原因仍见“待确认”。

### 匹配语义

- 匹配是连续、精确、区分字符的；不会自动跳过标点和空格，也不会做大小写、繁简或同音归一。
- `check` 在首个已结束词处短路。
- “查找全部”会沿当前 Trie 分支继续前进，并把该次起点得到的命中字符串加入结果；随后外层扫描根据已消费长度推进。
- `replace` 使用命中词数组执行 `str_replace()`，不会改变原始传入变量或数据库内容。

## 性能考虑

| 阶段 | 复杂度/成本 | 优化措施与限制 |
|---|---|---|
| 构建 Trie | 时间和内存约为 `O(词库总字符数)` | `Dict::build()` 从数据库 `pluck('word')` 一次性加载全量词库；构建结果写入 `py-sensitive-word:dict` |
| 文本扫描 | 近似 `O(N × Lmax)` 最坏情况，`N` 为文本字符数、`Lmax` 为最长可走前缀 | `check` 命中即停；实现无 AC failure link，不能保证 `O(N + matches)` |
| 命中词/替换 | 需要扫描更多分支并保留命中数组 | 仅在调用方需要明细或脱敏文本时使用 |
| 词库写入 | 新增使用一次 `whereIn` + 一次批量 `insert`；删除使用 `whereIn()->delete()` | 避免逐条数据库往返；写后只删除缓存 |
| 缓存 | 共享 `sys_tag` 缓存 + `sensitive_words()` 内静态对象 | 减少重复查库/建树；长驻进程中的对象刷新语义需额外关注 |

## 默认词库导入规则

`Poppy\SensitiveWord\Commands\InitCommand` 注册手动命令 `py-sensitive-word:init`，用于把 `resources/def/words.txt` 一次性导入数据库。资源文件当前为 5,705 行（按原始行统计 5,680 个唯一值，含 1 个空行）。命令不在调度器中注册。

导入策略是：用文件第一行判断是否已经导入、对原始行执行 `array_unique()`、逐行 `trim` 后批量写入。该命令面向初始化，不是可重复同步或增量合并工具。完整链路见 [flows.md](flows.md) 的“默认词库批量导入流程”。

## 待确认

- 路由和 SEO 文案保留“添加/编辑”及可选 `{id?}`，但 `WordController::establish()` 不接收 ID、`Action\Word::establish()` 也不更新已有记录；需确认是否应去除编辑语义或补全编辑能力。
- 迁移中的 `word` 长度为 50，但 Action 未声明 `max:50`；超过长度时会把错误推迟到数据库。是否需要在业务校验阶段明确限制？
- 数据表没有唯一索引，`establish()` 只排除数据库中已存在的词，未对同一次提交中的重复行执行 `unique()`；是否允许产生重复记录？
- `InitCommand` 用带换行符的原始第一行查询数据库，写入时又会 `trim`，且命令导入后不删除 `dict` 缓存；需确认该初始化命令是否需要修正幂等与缓存失效行为。
- `Words` 是单例，`sensitive_words()` 还保留静态实例；`illegalWords` 和 `searchAllIllegal` 未在每次检测前重置，后台写操作也无法替换当前长驻进程中的对象。需确认项目是否运行 Octane、常驻队列消费者或其他长生命周期 PHP 进程，以及这些状态是否需要请求级清理。
- 当前扫描在消费部分 Trie 前缀后会跳过相应字符，且没有 AC failure link；需用产品词表确认是否要求发现重叠词、前缀中重新起始的词和所有短词命中。
- 仓库没有记录“为何选择轻量 Trie 而非 AC 自动机”的设计决策；如词库或文本规模继续增长，需确认可接受的 P95 检测延迟与内存预算。
